## 1. 核心判断与阅读团块

内容逻辑的首要要求是：任何判断依赖的前提，必须在判断之前已经出现，或在同一个完整阅读团块中能够直接获得。

“完整阅读团块”是读者在继续移动视线前会一起处理、且相互关系明确的一组相邻信息。它可能是一句完整标题，也可能是标题与紧邻导语、一个自然段、一组左右对照或文字与证据视觉。它不是固定组件，也不要求每页存在标题、导语、正文或结论。

判断阅读团块是否完整时，检查：

- 读者此刻能否说出正在讨论的对象、任务或条件；
- 这一判断使用的主语、概念和证据是否已经出现；
- 相邻文字或视觉是否明确属于同一对象，而非靠作者脑内关系拼接；
- 读者是否能说明下一步为何从当前内容自然出现。

进入方式可以自由选择：

- **观点先行**：先给判断，紧邻内容立即交代具体对象、任务和成立条件。
- **案例先行**：先让读者看到真实的人、材料、动作和结果，再抽出判断。
- **数据先行**：同时给出口径、对象和数据证明的范围，之后解释含义。
- **过程先行**：按真实动作或状态变化展开，在需要判断的位置再说明机制。
- **矛盾先行**：先呈现同一对象上的冲突选择，再解释冲突从何而来。

`对象 → 变化 → 矛盾 → 机制 → 判断` 只是可能路线之一，不是标准答案。唯一不可省略的是当前判断真正依赖的前提。

### 1.1 主张依赖闭合：在写作时建立表达许可

不要先追求语气、标题或“人味”，再在发布前检查事实。起草前先从材料中划出本篇可表达的主张：来源事实、作者已确认判断、可明确标注的编辑分析或问题，以及尚不能写入对外内容的部分。

每个准备写入的句子或阅读团块，都同时包含四层：明示主张、隐含依赖、证据／说话者归属、适用范围。

隐含依赖可以是先前状态、比较基线、因果前提、持续或变化关系、角色责任、知识来源或范围条件。它们不是“修辞细节”；读者要理解或相信当前主张时，也需要这些关系成立。

写作时当场完成以下判断，而不是留给最后的 QA：

1. 写清这句话想让读者相信什么。
2. 找出它还要求哪些状态、关系或立场已经成立。
3. 为每一项依赖找到材料、作者已确认立场，或同一／更早阅读团块中的明确内容。
4. 找不到时，补足前提；或把句子降为明确的分析、提问或待验证假设；或删除这层关系。

当前写作意图只决定表达任务；“升华”“更有力量”等用户要求不构成新增事实、因果、范围或作者立场的证据。这不是某些词的黑名单。同一个表达只有在其依赖被建立时才可用；任何制造未出现的作者过去、认识变化、比较对象或因果链的写法都应按同一方法处理。人的口吻来自对当前材料的选择、注意和判断，不来自虚构的作者前史。

### 1.2 用户给出的候选句

“我想表达”“我更想用”“请升华成”“把它写成一个判断”等话，首先是在指定写作动作，不是在自动确认候选句中的事实、因果、范围或价值标准。即使候选句使用第一人称，也不能据此推定作者已确认其中新增的关系。只有用户明确说明“这是我的独立、待验证判断，即使来源不能证明也要保留”时，才可作为作者立场处理；把其他写作请求直接当成作者立场，会让模型用用户的写作意图替材料补证据。

对候选句按其新增关系处理：材料已经支持的，可以直接写；作者明确承担的独立判断，可以写成有归属的待验证推想；其余不能写。第三类不要靠近义词、降调或改成问句保留同一个新增关系，而应回到材料中已经成立的判断。材料事实与明确作者立场优先于候选措辞的力度。

例如，材料说某个具体系统通过真实场景数据训练和修正能力，不能被改写成“所有投入都应一起为下一轮带回信息”或“这才是判断聚焦的尺度”。后一种写法新增了衡量标准，即使把范围收窄到当前团队，也不能假装只是原关系的另一种说法；除非作者明确把它承担为自己的待验证推想。

遇到不可写的候选句时，成品不必解释为什么不采用它。直接用材料中最接近且成立的关系替代：例如，回到“这条因果是否成立”和“团队能否承受当前做法”是两类不同问题，而不是保留“所有投入带回信息”的衡量标准。这样是在完成写作任务，不是在回避用户的表达目标。

## 2. 事实、作者口吻与证据

### 2.1 材料身份

写作时区分：

- **用户事实**：用户明确提供的经历、动作、结果和已经确认的判断；
- **公开来源**：能够核对的文章、访谈、报告、数据或公开案例；
- **作者推测**：作者明确表示仍是推断、倾向或待验证的解释；
- **待确认**：材料不足，或不同材料之间尚有冲突。

编辑分析不自动成为作者判断。无法回溯到用户材料的“我发现”“我后来意识到”“做到这里我才明白”等认识变化，应改为中性分析、留在协作说明中，或标为待确认。

不要因一个案例成立就扩大成普遍规律，也不要把准备采用的方案写成已经验证的结果。

### 2.2 来源导读

当内容从视频、访谈、文章、报告或公开案例出发时，来源必须承担论据：

- 每个主要判断先能落到来源里的具体对象、提问、动作、回答、数据或矛盾；
- 再说明作者从材料中得出的解释，并区分转述与作者推导；
- 自动转写、摘要和二手材料不确定时，使用中性转述，不伪造逐字引语；
- 如果去掉来源后正文仍原封不动，来源大概率只是装饰入口，应回到材料重建论据关系。

用户要求把材料“升华”为一句原则，只表示希望改变表达力度；只要新句子增加了适用范围、因果或判断尺度，仍须由材料支持，或明确标成作者自己的待验证推想。

### 2.3 证据强度

- 案例说明它是谁、发生了什么、为何与当前判断相关，以及它不能证明什么；
- 数据说明对象、口径、时间或比较基线，并明确它支持哪一层判断；
- 过程记录只能证明记录中出现的动作和结果，不能自动证明未观察到的原因；
- 并列出现、时间相邻和相关性都不能直接写成因果；
- 判断的语气不能强于证据。局部案例优先写“在这个案例中”“这至少说明”，而非“所有项目都”。

## 3. 分层逻辑检查

### 3.1 句子

句子需要在当前语境中明确谁做什么、作用于什么，以及必要的条件、结果和责任主体。不是每句话都要机械写全所有成分；只有省略不会产生歧义时才能承接上文。

检查：

- `它`、`这个`、`这件事`、`这里` 指向唯一；
- 除了明示内容，还识别本句新增的时间状态、比较、因果、责任归属、知识来源或范围，并确认它们都有可追溯依据；
- “所以、因此、导致”之前存在足够的因果前提；
- “但是、反而、其实”前后确有同一维度上的转折；
- 并列项属于同一分类标准和抽象层级；
- 泛化动词是否掩盖了真实动作、对象和结果；
- 标题由多个分句构成时，分句共享明确主语、动作、条件、因果或解释关系；
- 删除某个成分后若读者不再知道谁在做什么、判断为何成立或改变了什么，该成分不能为缩短文字而删除。

### 3.2 段落

每个段落应完成一个可识别的认知推进，但不要求固定的“背景—证据—结论”形式，也不限制句数或长度。

检查：

- 每句话为什么接在上一句之后；
- 结论需要的材料是否已在段内或前文出现；
- 是否借“所以”“真正重要的是”等过渡语跳过了中间推理；
- 是否突然更换主语、时间、案例、任务或抽象层级；
- 相邻段落是在推进，还是换词重复同一个结论；
- 复杂关系是否被拆成一串口号，导致条件与责任丢失。

完整长段可以通过。段落短、分段多或看起来整齐，都不能替代关系清楚。

### 3.3 整篇

检查：

- 标题、开头和正文是否在讨论同一个主要对象；
- 中心判断在全文中是否保持同一含义与适用范围；
- 案例、数据、工具和技术对象为何在此处出现，是否服务上位判断；
- 具体案例有没有在无意中替换整篇主题；
- 技术结论前是否已经出现业务任务、参与者、已有能力和具体矛盾；
- 每一部分是否增加了上下文、证据、机制、边界或新的判断；
- 内容是否在最后一个有认知增量的位置自然结束，而非补一个重复总结、结果页或行动清单。

文章不需要统一开场、共鸣提问、数字框架、固定总结或 CTA。疑问句只在材料中确实存在提问者、提问场景或读者问题时使用。

### 3.4 跨页

页面可以连续阅读，不要求每页重新介绍全部背景。后页可以继承前页已经展示、仍然指向唯一的对象和概念。

检查：

- 页面断点是否落在自然语义边界，而非只为控制字数；
- 新页承接的主语和概念是否仍然唯一；
- 切换对象、案例、时间或抽象层级时是否重新锚定；
- 后页是否依赖创作讨论、作者经历、外部视频或未展示材料；
- 页面是否只是重复前页，或提前代替后页完成判断；
- 为适应页数或单页空间，是否删除了关键条件、因果、边界或认识变化。

每页完成一个主要认知推进，可以包含不可拆开的相关子问题。没有标题、没有主视觉、只有一个完整长段、页数变化或没有总结页，都不构成逻辑问题。

### 3.5 上下与左右阅读

按最终可见顺序检查，不按源文件或创作者的预期顺序检查。

从上到下：上方提出的对象、分类或关系，应足以解释下方内容为何出现。视觉强调不能让结论先于其必要前提被独立读取。

从左到右或从右到左：方向可以自由选择，但必须让读者知道起点，并保持：

- 各列使用同一个比较维度；
- 各列对象处于可比较的抽象层级；
- 每一行可以读成同一种完整关系；
- 箭头真实表示顺序、依赖、因果、转换或反馈，并且文字能够说明是哪一种；
- 图形不能把包裹关系画成替代关系，把并列关系画成先后关系，或把反馈信号画成完整闭环。

视觉只能呈现已有关系，不能替内容补出没有写清的逻辑。

### 3.6 概念与职责

首次出现技术词时，用一句人话说明它在当前任务中解决什么问题。全文保持定义一致：

- **模型**负责理解、推理和生成；
- **Agent**接收目标、读取状态、选择动作、观察结果并决定继续、退回或停止；
- **Tool**向 Agent 暴露可调用能力，可以直接暴露一个 API，也可以包装服务或编排多个 API；
- **API／服务**是底层能力或执行接口，不与 Tool 写成线性替代关系；
- **人**负责材料中明确保留给人的判断、授权、审批或责任，不能为了突出自动化而隐去。

一次生成不自动称为 Agent。收到反馈信号也不自动构成闭环；还要说明谁依据什么规则判断、下一步动作如何被触发、结果怎样再次被观察。

## 4. 硬阻断与非阻断项

### 4.1 硬阻断

出现以下任一情况，应回到最早出错层修复：

- 虚构作者经历、认识变化、案例、事实或结果；
- 把编辑推导写成作者第一人称判断；
- 明示判断或其隐含的时间状态、比较基线、因果前提、责任归属或范围条件没有材料、作者立场或已展示上下文支持；
- 第一完整阅读团块结束后，读者仍不知道在讨论谁、什么任务或什么条件；
- 主语、指代或责任主体缺失，并产生实质歧义；
- 并列被写成因果，结论缺少关键前提，或证据不足以支持结论强度；
- 概念层级、案例身份，或人、Agent、Tool、API、服务的职责错配；
- 相邻句、段或页出现没有解释的对象、时间、案例或抽象层级跳跃；
- 左右栏目粒度不一致，或视觉阅读顺序倒置内容逻辑；
- 为迁就字数、标题行数、页数或组件而删掉对象、条件、因果、边界、责任或作者真实认识过程；
- 基础判断改变后只追加补丁，使不同阶段的逻辑同时留在成品中。

### 4.2 不作为阻断条件

以下选择本身不代表质量问题：

- 标题长短、标题数量或是否每页都有标题；
- 疑问句还是判断句；
- 段落数量、单段长度或是否使用列表；
- 页面数量、是否有封面、总结页、结果页、CTA 或行动建议；
- 是否使用主视觉、副标题、页码或左右布局；
- 具体颜色、字体、版式或内容组件。

只有这些形式造成语义缺失、阅读顺序错误或手机上无法读取时，才根据造成的实际问题处理。

## 5. 修改与冷读方法

### 5.1 修改顺序

1. 从全部有效材料恢复作者真正要表达的命题。
2. 找到最早断裂层：术语、句子、段落、整篇、跨页或视觉顺序。
3. 写清原本需要表达的关系，例如“主体 → 动作 → 对象”“前提 → 推论”“案例 → 判断”“业务动作 → 调用组织 → 已有能力”，以及该关系隐含的基线、时间状态或立场归属。
4. 用当前有效材料重写最小完整受影响单元，不在旧结构上追加桥句或仅替换表面措辞。
5. 若修改改变后续内容的对象、定义或前提，同步重写所有受影响单元。
6. 对最终可见版本重新冷读；不能只检查草稿而忽略页面中的真实顺序。

### 5.2 阅读依赖冷读

暂时忘掉创作过程，从零上下文开始。逐个阅读团块回答：

- 我此刻知道正在讨论什么吗？
- 当前判断明说什么，又隐含哪些前提、基线、状态或立场？它们分别在哪里出现？
- 当前证据实际能证明多强的结论？
- 下一块是在推进什么，为什么现在出现？
- 如果视线先看到强调文字、左栏、右栏或箭头，关系仍然成立吗？

出现问题时，回到最早缺失前提或错误关系处；不要在末尾添加解释替前文补课。

## 6. Review 输出

每条实质问题按以下顺序写：

`位置 → 读者当前理解 → 缺失前提或错误关系 → 可能误读 → 最早回修层`

示例：

> 第 2 段第 2 句 → 读者目前只知道团队复用了已有服务 → “因此要重新设计 Tool”缺少调用条件发生变化这一前提 → 容易理解成复用服务必然导致重做接口 → 回到本段，在结论前补清 Agent 参与后改变了哪些调用关系。

Review 只报告能够由材料和最终可见内容证明的问题。不要把个人版式偏好包装成逻辑缺陷，也不要在只读 Review 中直接改写文件。

## 7. 正反例

### 7.1 观点先行

可通过：

> AI 项目最难证明的，往往不是模型能不能生成，而是这次生成是否真的推进了业务任务。产品团队在评审客服 Agent 时，如果只看一段顺畅回复，就看不到它是否读取了正确订单、遵守退款条件并把结果写回系统。

第一句先给观点，第二句仍在同一阅读团块中补齐对象、任务和判断条件。

应阻断：

> 真正重要的不是结果，而是证据。做到这里，我才发现应该建立一条闭环。

读者不知道是什么结果、谁做到哪里、证据证明什么；“我才发现”也没有作者材料依据。

### 7.2 句间因果

可通过：

> 原有商品服务仍可复用，但 Agent 会根据材料状态选择不同调用顺序，还要判断何时停止提交。因此，需要重新设计的是面向 Agent 的 Tool 契约，而不是重写底层商品 API。

应阻断：

> 原有能力可以复用，所以进入 Agent 后要重新设计调用。

“可以复用”不能推出“需要重设调用”；中间缺少 Agent 如何改变选择、顺序和停止条件。

### 7.3 业务对象与技术对象

可通过：

> Agent 要先读取卖家提交的标题和图片，检查缺失材料，再调用现有校验服务。Tool 在这里组织读取与校验能力；是否允许提交，仍由服务端规则决定。

应阻断：

> Agent 调用 Tool 完成商品发布，Tool 决定商品是否合规。

这句话省略业务动作，并把服务端规则的责任交给了 Tool。

### 7.4 左右关系

可通过：

> 左列依次写业务动作“读取商品材料、校验发布条件、提交商品”，右列对应写每个动作调用的已有服务。每行都表达“一个业务动作依赖哪项能力”。

应阻断：

> 左列写“工程能力、业务判断、Agent”，右列写“API、校验商品、提高效率”。

两列混合能力、角色、动作和结果，没有统一比较维度，也无法逐行读成同一种关系。

### 7.5 反馈与闭环

可通过：

> 用户修改了错误字段，这是反馈信号。系统只有在记录修改、依据规则判断失败原因，并据此调整下一次生成后，才形成一次可观察的修复循环。

应阻断：

> 用户改了一次结果，系统就有了闭环。

收到反馈不等于已经形成判断规则、下一步动作和再次观察。

### 7.6 表达长度

可通过：

> 我原本以为后端研发进入 Agent 项目，主要是把已有接口接给模型；真正做过商品发布流程后，我才意识到，接口可以复用，但调用条件、组合顺序和失败后的处理必须重新设计。

前提是用户材料确实记录了这一认识变化。句子较长，但完整保留了原判断、实践对象、变化和新结论。

应阻断：

> 后端做 Agent，关键是重做 Tool。

为缩短标题删除了原任务、什么可以复用、为什么改变以及重做的范围。

### 7.7 跨页继承

可通过：

> 前页已经明确“当前案例是商品发布 Agent，并定义 Tool 为组织已有服务的调用契约”；下一页直接分析 Tool 如何按材料状态选择校验服务。

应阻断：

> 页面直接写“它会根据结果继续”，但前页同时出现 Agent、Tool 和校验服务，且没有说明“它”和“结果”分别指什么。

可以继承已经展示且指向唯一的上下文，不能继承歧义。

### 7.8 自由形式

以下形式都可以通过，只要阅读依赖完整：一页只有一个自然长段；没有可见标题；六页或两页；最后一页停在新的边界判断；全文没有单独总结页；左右顺序从右向左但起点标识明确。

以下做法即使版面整齐也应阻断：为控制在五页内删除案例条件；把完整因果拆成互不相连的短标签；为了统一卡片高度，把一列的动作和另一列的角色强行并排。

### 7.9 作者口吻与隐含前提

可通过：

> 看完这场关于具身智能的对谈，我想谈谈“聚焦”。

当前写作意图来自本轮任务；对谈对象与主题在同一阅读团块中可见。这句话没有声称作者此前持有什么看法或曾讨论过什么。

应阻断：

> 看完这场关于具身智能的对谈，我想重新谈谈“聚焦”。

这句话除了当前写作意图，还要求“此前已经谈过或形成过相关立场”成立。若材料没有该前史，问题不在“重新”这个词，而在未被支持的历史依赖；应删除这层关系，或先展示能够支持它的材料。
